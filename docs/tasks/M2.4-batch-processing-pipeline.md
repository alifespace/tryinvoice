# M2.4-batch-processing-pipeline：增量批处理编排与持久化

- **目标**：把 M2.1 的分层提取器与 M2.2/M2.3 已验收的确定性规则串成可重复执行的批处理管线，持久化处理结果并暴露 `POST /batches/{id}/process`。
- **前置依赖**：`M2.1-document-extractor`、`M2.2-deterministic-rule-engine-part1`、`M2.3-deterministic-rule-engine-part2` 已验收范围。
- **范围与约束**：
  - 仅提取 `ocr_status=pending` 的新增凭证；随后基于批次内全部已完成凭证，确定性地重算分区、去重、配对、交易和机场缺漏告警。
  - 持久化 `transactions`、`transaction_documents`、`reimbursement_batches` 与 `jobs`；重复调用不得重复提取旧凭证、生成重复交易或改变稳定交易 ID。
  - 与 `is_user_verified=true` 交易共享凭证的自动计算结果必须跳过；人工确认交易及其人工字段不得被覆盖或删除。
  - 业务写入须具备事务边界；失败时作业状态可追踪、业务数据无半写，错误信息不得包含票据原文、凭证或底层异常详情。
  - 现存 `M2.3-S3` 代码是未验收候选，不是完成成果。Planner 必须先核对当前实现与门禁结果，再拆分职责并降低最大圈复杂度至 10 以下，不得通过删减既定行为规避门禁。
  - Planner 应优先把“提取与规则编排”和“交易/批次持久化同步”划成职责清晰、可独立验证的 Subtask；计划累计改动量不得超过 1,200 行，为返工保留至少 300 行余量。
  - 只使用 Mock/内存生成样本验证，不接入真实 OpenAI、对象存储或生产 Supabase；不包含 `GET /batches/{id}/transactions`、`PATCH /transactions/{tx_id}`、导出、后台队列或数据库迁移。
- **验收标准**：
  - `POST /batches/{id}/process` 完成首次处理并返回作业与处理统计；未认证请求为 `401`，他人批次不可见。
  - 无新增凭证重跑保持幂等；新增凭证只触发增量提取，但会基于全部已完成凭证重算规则结果。
  - 人工确认交易及人工字段在重跑后保持不变；未确认且已失效的陈旧交易可安全清理。
  - 提取失败、存储暂不可用与持久化异常按设计分流；业务异常回滚且日志、响应、作业错误均不泄露敏感信息。
  - OpenAPI 契约与应用路由一致；测试、lint、类型检查、安全审计、覆盖率、复杂度与重复代码 7 项门禁全部真实通过，最大圈复杂度不超过 10。
  - 本 Task 按独立基线核算，总改动量不超过 2,000 行；测试满足 `Test:Feat <= 1.3` 或新增测试低于 450 行之一。
